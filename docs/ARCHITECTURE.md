# システム設計書 (ARCHITECTURE.md)

このドキュメントでは、`bunka` のシステムアーキテクチャ、ディレクトリ構造の意図、技術スタック、およびモジュール間のデータフローについて説明します。

---

## 1. システムの概要と目的

`bunka` (分化) は、浮動小数点数（例: `0.142857`）やパーセント表記（例: `10%`）の数値入力を、有理数としての最適な既約分数形式（例: `1/7`, `1/10`）に近似変換するアプリケーションおよびライブラリです。

### 開発の目的
- **高精度な有理数近似**: 小数点数から人間が直感的に理解しやすい分数表現への高速かつ正確な変換。
- **マルチインターフェースの提供**: 
  - 自動処理やスクリプト連携に適した軽量な **CLI ツール**。
  - 最前面に常駐し、直感的に操作できるインタラクティブな **デスクトップ GUI アプリ**。
- **高効率と省リソース**: メモリ割り当て（ヒープ）を抑えた高速な近似アルゴリズムと、最適化されたフットプリントの実現。

---

## 2. 技術スタック

本プロジェクトは以下の技術要素で構成されています。

### 2.1 開発言語
- **Rust (Edition 2024)**: 安全性、並行性、および実行速度を両立する言語仕様。

### 2.2 主要ライブラリおよびフレームワーク
- **eframe / egui (v0.35.0)** (GUIフィーチャー有効時):
  - Rust 向けの即時モード (Immediate Mode) GUI ライブラリ。
  - 枠なし (`decorated: false`) や背景透過 (`transparent: true`)、最前面表示 (`with_always_on_top`) などの高度なウィンドウ制御を実現。
- **windows (v0.62.2) & winapi (v0.3.9)** (GUIフィーチャー有効時):
  - Windows API へのアクセスを提供。
  - Windows 環境における多重起動を防止するための Named Mutex 制御に使用。
- **common_lib** (ローカルクレート `path = "../common_lib"`, GUIフィーチャー有効時のみ):
  - `gui` Cargo feature 有効時のみオプショナルで依存。Windows デスクトップ向けの二重起動防止などのプラットフォーム共通ロジックを提供。

## 3. アーキテクチャとディレクトリ構造の意図

プロジェクトは以下のような構成で整理されており、責務が明確に分離されています。

```text
bunka/
├── .agents/
│   ├── AGENTS.md               # AI向けの開発ガイドラインとルール
│   └── INSTRUCTIONS.md         # AI向けコーディングスタイル指示書（規約）
├── .github/
│   └── workflows/
│       ├── ci.yml              # Windows環境でのビルド・テストCI
│       └── release.yml         # バージョン検知と自動リリースCD
├── docs/
│   ├── ARCHITECTURE.md         # 本書（システム設計書）
│   ├── DIAGRAM.md              # 処理フロー・構成図 (Mermaid)
│   ├── FOOTPRINTS.md           # バイナリサイズ・性能実測値
│   ├── PROJECT_TEMPLATE_GUIDE.md # プロジェクト初期設定ガイド
│   ├── SPEC.md                 # 要件およびアルゴリズム仕様書
│   ├── TEST_REPORT.md          # 単体テスト・手動テスト検証報告書
│   └── images/                 # スクリーンショット等のアセット
├── src/
│   ├── main.rs                 # フィーチャーに基づく起動分岐
│   ├── lib.rs                  # コアアルゴリズムと共通パース処理 (CLI/GUI非依存)
│   ├── cli.rs                  # CLI引数解析と標準入出力処理
│   └── gui.rs                  # eguiによるGUI描画とウィンドウ制御
├── Cargo.toml                  # 依存関係とリリースプロファイル設定
└── CHANGELOG.md                # 変更履歴管理
```

### ディレクトリ設計の意図
- **コアロジックの純粋性 (`src/lib.rs`)**: 
  - 近似アルゴリズム（連分数展開）や入力値のパース処理は、CLIやGUIといったI/O層から完全に独立しています。これにより、GUIフィーチャーを外してビルドする際にも依存関係を極小化でき、テスト容易性も確保されます。
- **環境に依存しない構成管理 (`docs/`)**:
  - すべてのドキュメントファイルは `UPPER_SNAKE_CASE.md` 形式で統一し、`docs/` 配下に集約することで、プロジェクトルートの視認性を高めています。また、ドキュメント内の相互参照リンクはすべて相対パスで記述されています。
- **フィーチャーベースの分離**:
  - `Cargo.toml` の `gui` フィーチャーを切り替えることで、フットプリントを最小限に抑えた CLI 専用バイナリと、リッチな GUI バイナリを同一コードベースから作り分けられるように設計されています。

## 4. データフローとモジュール間連携

`bunka` のデータ処理フローは、ピュアな処理を担当するライブラリコア（`src/lib.rs`）を中心に設計されています。

### 4.1 CLI 実行時のデータフロー
1. `main.rs` から `cli::run_cli()` が呼び出されます。
2. `cli.rs` が `std::env::args()` からコマンドライン引数をパースします。
3. 数値文字列を `lib::parse_decimal_or_percent()` に渡し、パーセント表記や通常の小数形式を解析して `f64` 実数を得ます。
4. 解析された数値、およびオプション引数（最大分母 `-d`, 許容誤差 `-t`）を `lib::approximate_fraction()` に渡します。
5. 得られた結果（分子、分母）を `stdout` に `分子/分母` 形式で出力して終了します。

### 4.2 GUI 実行時のデータフロー
1. `main.rs` から `gui::run_gui()` が呼び出されます。
2. `gui.rs` 内で `common_lib::desktop::acquire_single_instance()` が呼び出され、Named Mutex による二重起動チェックを行います。既に起動中であれば即座に終了します。
3. 初回起動時、`eframe::run_native()` により `BunkaGuiApp` が初期化され、egui のイベントループが始まります。
4. ユーザーがテキストフィールドに数値を入力すると、`BunkaGuiApp::recalculate()` が走ります。
5. `recalculate` 内部で `lib::parse_decimal_or_percent()` を用いてパースを試み、成功した場合は `lib::approximate_fraction()` を実行して構造体（`BunkaGuiApp`）の状態（`numerator`, `denominator`）を更新します。パース失敗時は以前の値を保持し、クラッシュを防止します。
6. `eframe::App::ui()` が再描画（repaint）を検知し、最新の計算結果を画面中央に描画します。
7. 「Copy」ボタンが押された場合、UIコンテキストを介してOSのクリップボードへ `分子/分母` の文字列がコピーされます。
