# 開発指示書 (INSTRUCTIONS.md)

このドキュメントでは、AI（および開発者）が `MyBunka` プロジェクトのコードを修正・追加する際に遵守すべきコーディングスタイル、設計方針、および出力フォーマットについて説明します。

---

## 1. 命名規則

Rustの標準的な API Guidelines に厳格に従ってください。

- **変数・関数・モジュール・マクロ名**: `snake_case` (小文字スネークケース)
- **構造体・トレイト・列挙型・型エイリアス**: `UpperCamelCase` (アッパーキャメルケース)
- **定数・静的変数**: `SCREAMING_SNAKE_CASE` (大文字スネークケース)
- **ファイル命名**:
  - ソースコード (`.rs`): `snake_case` (例: `cli.rs`)
  - ドキュメント (`.md`): `UPPER_SNAKE_CASE` (大文字スネークケース)

---

## 2. エラーハンドリング方針

- **ライブラリ層 (`lib.rs`)**: `panic!` や `unwrap()`、`expect()` の使用を原則禁止します。
- **CLI層 (`cli.rs`)**: 標準エラー出力 (`eprintln!`) に分かりやすいエラーメッセージを出力し、`std::process::exit(1)` で即座に終了させてください。

---

## 3. コンポーネントおよびモジュールの分割基準

- **純粋ロジックとI/Oの分離**: プラットフォームに依存しない「純粋なビジネスロジック」はすべて `lib.rs`に集約します。
- **UIモジュールの分離**: コマンドラインのプレゼンテーションロジックは `cli.rs` にカプセル化します。

---

## 4. 自動ドキュメンテーションと更新ルール (モジュール化退避)

コードの変更、リファクタリング、機能追加、バグ修正、依存ライブラリ更新を行った場合、`docs/en/`（英語版）および `docs/ja/`（日本語版）の2フォルダを作成し、完全同期させて管理します。

## 5. 品質管理・ローカル事前検証ルール (モジュール化退避)

- **ユニットテストの追加・拡充**: 新機能追加やコアロジック変更時は、可能な限り関連するユニットテストコードを追加・拡張すること。
- **コード規模とリファクタリング（モジュール分割）**: 単一のソースファイルの行数が **1,000 行** を超えた場合、サブモジュールへの分割や構造化リファクタリングを提案すること。
- **ローカルでの事前検証プロセス** (※ `.md` のみ変更時は全スキップ可):

  1. `cargo test` （テストの合格）
  2. `cargo clippy --all-targets -- -D warnings` （Clippyの警告・エラーゼロ）
  3. `cargo fmt --check` （コードフォーマットの完全準拠）
  4. `cargo doc --no-deps --document-private-items` （Rustdocビルドエラー・警告ゼロ）
