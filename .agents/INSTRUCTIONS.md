# 開発指示書 (INSTRUCTIONS.md)

このドキュメントでは、AI（および開発者）が `bunka` プロジェクトのコードを修正・追加する際に遵守すべきコーディングスタイル、設計方針、および出力フォーマットについて説明します。

---

## 1. 命名規則

Rustの標準的な API Guidelines に厳格に従ってください。

- **変数・関数・モジュール・マクロ名**: `snake_case` (小文字スネークケース)
  - 例: `approximate_fraction`, `parse_decimal_or_percent`
- **構造体・トレイト・列挙型・型エイリアス**: `UpperCamelCase` (アッパーキャメルケース)
  - 例: `CliOptions`
- **定数・静的変数**: `SCREAMING_SNAKE_CASE` (大文字スネークケース)
- **ファイル命名**:
  - ソースコード (`.rs`): `snake_case` (例: `cli.rs`)
  - ドキュメント (`.md`): `UPPER_SNAKE_CASE` (大文字スネークケース)
    - 例: `ARCHITECTURE.md`, `INSTRUCTIONS.md`, `TODO.md`
    - ※ ただし、標準的・慣習的なファイル（`README.md`, `LICENSE`, `CHANGELOG.md`）は除きます。

---

## 2. エラーハンドリング方針

堅牢で予期せぬクラッシュを起こさないコードを記述するためのルールです。

### 2.1 ライブラリ層 (`lib.rs`)
- ライブラリ内では `panic!` や `unwrap()`、`expect()` の使用を原則禁止します。
- 失敗する可能性のある処理（パースなど）は、`Result<T, E>` または `Option<T>` を戻り値として返してください。
  - 例: `parse_decimal_or_percent` 関数はパースエラー時に `Result<f64, ParseFloatError>` を返します。

### 2.2 CLI層 (`cli.rs`)
- コマンドライン引数のパースエラーや無効なパラメータを検出した場合、標準エラー出力 (`eprintln!`) に分かりやすいエラーメッセージを出力し、`std::process::exit(1)` で即座に終了させてください。

## 3. コンポーネントおよびモジュールの分割基準

コードの責務を明確にし、テスト容易性と保守性を確保するための基準です。

- **純粋ロジックとI/Oの分離**:
  - 計算アルゴリズムや文字列解析など、プラットフォームや入出力装置に依存しない「純粋なビジネスロジック」はすべて `lib.rs`（または `lib.rs` から呼び出される純粋なモジュール）に集約します。
- **UIモジュールの分離**:
  - コマンドラインのプレゼンテーションロジックは `cli.rs` にカプセル化します。
- **ファイル規模の上限と分割推奨 (1000行制限)**:
  - 単一のソースコードファイル（`.rs` 等）の行数が 1000 行を超えた（または達しそうになった）場合は、可読性と保守性を保つためサブモジュールへの分割や構造化リファクタリングを推進します。

## 4. AI 出力フォーマットの指定

AIが修正や提案を行う際の効率的なやり取りのためのフォーマット指定です。

- **解説は最小限にする**:
  - 実装方法に関する長大な能書きや解説は避け、簡潔な箇条書き、または変更の理由（Rationale）のみを数行で示してください。
- **動作する完結したコードブロックの提示**:
  - 部分的な切り貼りコードではなく、変更箇所の前後が明確にわかる完結した diff や、必要であれば置き換え用のコード全体を提示してください。
- **相対パスリンクの徹底**:
  - ドキュメント内のファイル参照は、特定のユーザー環境に依存しない相対パス（例: `../docs/SPEC.md`）を使用してください。絶対パス（`file:///`）の埋め込みは厳禁です。
- **自動更新ルールの厳守**:
  - 変更が Markdown ファイルのみである場合を除き、ソースコードを変更した場合は必ず `../CHANGELOG.md` を更新し、`../docs/SPEC.md` や `../docs/TEST_REPORT.md` との整合性をセルフチェックしてください。
